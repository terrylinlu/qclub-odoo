# qclub_billiard 需求规格：阶段 5（员工日常：实时看板与到店提醒）

放置路径：`docs/spec/phase5.md`　状态：**已定稿**（2026-11-18 起草，当天评审通过）
每条需求必须有至少一个测试，测试名或 docstring 中带编号（如 `test_rt_001_board_shows_occupancy`）。
本阶段新增前缀 **RT**（Real-Time，第 A、B 节）；定稿后加入 `tools/make_report.py` 的覆盖检查。
界面文字为英语，示例文字以本文件为准。范围仅限 Q Club 网站（billiard 模块专属功能，不涉及 AUSHARE）。

**一句话**：员工后台有一个实时更新的桌台占用看板，顾客在网站上的关键动作（新预约、付款确认、取消、有人加入找球友帖）几秒内以弹窗提醒在线员工，不用手动刷新页面。

**依赖与已知限制**：这轮设计建立在 Odoo 自带的 bus/WebSocket 推送机制上（穿刺 0 已验证测试/演示环境可用）。生产环境的 Nginx 反向代理目前缺少 `proxy_http_version 1.1`，WebSocket 握手会失败；这是运维配置问题，由你自行安排时间在上线前修复，不属于本模块代码范围。本轮不做"WebSocket 不可用时自动降级为轮询"的设计——如果握手失败，看板和提醒就是静态的，需要手动刷新，这个情况记为已知限制，不算 bug。微信/Telegram 机器人 Webhook 推送本轮不做，留待后续阶段。

## A. 实时看板（RT）

| 编号 | 需求 |
|---|---|
| RT-001 | 新增后台页面"Table Board"，仅 Q Club 网站的员工/管理员可见（同 `group_billiard_staff` / `group_billiard_manager`）；按桌台列出当前（此刻）占用/空闲状态，占用格显示预约编号、顾客姓名、结束时间；格子布局与顾客预约网格类似但这是后台独立页面，不是网格本身 |
| RT-002 | 看板数据通过 Odoo bus 推送更新：预约新建、确认、取消、到店、结算、未到场等任何改变"当前是否占用"的事件发生后，所有打开该页面的员工几秒内看到状态更新，不用手动刷新；WebSocket 连接失败时页面仍可打开，显示进入时的静态快照，不自动重试轮询（见上方"已知限制"） |
| RT-003 | 看板只显示"现在"这一个时刻的状态，不提供未来时段/其他日期的查看（那是现有顾客网格和 Bookings 日历视图的职责，不重复造轮子） |

## B. 实时提醒（RT）

| 编号 | 需求 |
|---|---|
| RT-004 | 以下四类事件发生时，向该网站当前在线（打开了后台任意页面）的员工/管理员弹出一条轻量提醒（toast，不阻断操作、几秒后自动消失或可手动关闭）：① 新预约提交（待付押金）② 押金付款成功（预约确认）③ 预约取消 ④ 找球友帖子有新玩家被接受加入 |
| RT-005 | 提醒内容只包含预约编号、桌台、时段、事件类型（如 "New booking QB2026-00123 awaiting deposit"），不包含金额、支付方式、顾客联系方式等敏感信息 |
| RT-006 | 提醒面向该网站所有当前在线的员工/管理员广播，没有"认领"或"已读"机制；员工离线时错过的提醒不会在重新上线后补发（与 NS-006/CFG-007 的邮件通知"不补发"规则一致） |
| RT-007 | 提醒不依赖邮件，走 Odoo 自带的站内实时推送（同 RT-002 的 bus 机制）；AUSHARE 网站的事件不会触发 Q Club 员工收到的提醒，反之亦然 |

## C. 电话预约录入

沿用阶段 4 已验收的后台 Bookings 表单（PAY-010）：员工点 Bookings 菜单的 **New** 按钮录入电话预约，标记 "No online deposit"。本阶段不新增专门的快速录入界面，不新增需求编号。

## D. 遗留与后续

- 微信/Telegram 机器人 Webhook 推送：本轮不做，草案里保留"可选"字样，留给后续阶段按需评估
- WebSocket 自动降级为轮询：本轮不做；如果生产环境长期无法修复 Nginx 配置，再评估是否需要降级方案
- 生产环境 Nginx `/websocket` 的 `proxy_http_version 1.1` 修复：由你自行安排，不在 Claude Code 操作范围内（AGENTS.md 红线：不操作生产）
