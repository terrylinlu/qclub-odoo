# 任务 3.3 设计说明：回复、申请加入、关闭联动与通知

分支：`feat/p3-3-board-join`　状态：**待评审**
对应规格（10 条）：BRD-010 至 BRD-015、BRD-017 至 BRD-019（`docs/spec/phase3.md`）；并把 BRD-029 的同意须知扩展到回复和申请

实现方式：评审通过后由 Codex 编码，Claude Code 运行测试并独立审查

## 一、用户看到什么

全部在预约页的帖子面板内，不跳转页面：

| 看的人 | 面板内容 |
|---|---|
| 未登录 | 帖子、已接受球友、回复（名字均为 Q Club Player）；**Apply to join** 和回复框点击后跳转登录，返回同一帖子 |
| 其他已登录顾客 | 同上并显示姓名；**Apply to join**（可附一句留言）、回复框 |
| 已申请的顾客 | 自己的申请状态（Waiting / Accepted / Declined）；待处理或已接受时可 **Withdraw** |
| 发帖人 | 多一个申请列表：姓名、留言、**Accept** / **Decline**；已接受的可 **Remove** |
| 帖子已关闭 | 全部只读，显示 "This post is closed." |

- 网格标记和当日列表的 "Join · N" 随已接受人数变化，名额满显示 "Full"，满了不能再申请
- 首次回复或申请前也要勾选社区须知（发帖已有，同一条记录，只需同意一次）
- 每次操作后刷新面板和网格；提示沿用 2.2 的红框方式，滚动到可见位置

## 二、数据模型

**`qclub.board.reply`（新）**：`post_id`、`partner_id`、`website_id`（取自帖子，存储）、`message`（必填，纯文本 1–500 字符）。

**`qclub.board.application`（新）**

| 字段 | 说明 |
|---|---|
| `post_id`、`partner_id`、`website_id` | 同上 |
| `message` | 可选，纯文本，最多 200 字符（第七节问题 2） |
| `state` | `pending` / `accepted` / `declined` / `withdrawn` / `removed` |

**数据库部分唯一索引**：`(post_id, partner_id)`，条件 `state IN ('pending','accepted','declined','removed')`（BRD-011；撤回的可以重新申请，第七节问题 1）。

"剩余名额" = 需要的人数 − 已接受人数，改为按申请计算。列表接口的字段集合不变（已合并测试固定了这些字段）。

## 三、不超额（BRD-013）

接受申请时，先对帖子这一行做一次真实更新，再统计已接受人数。

原因（与 2.2 的未付押金上限相同）：Odoo 使用 REPEATABLE READ，只加咨询锁刷新不了旧快照。真实更新会让并发的第二个请求发生序列化冲突，由 Odoo 重试，重试时看到最新人数，超额则返回 "No spots left."。用两个独立事务在真实 PostgreSQL 上测试，不 mock。

## 四、接口

全部 `type="jsonrpc"`，只在开启 Online Board 的网站可用，其他网站 404；写操作要求登录和 CSRF，只接受白名单参数。

| 路由 | 作用 | 校验 |
|---|---|---|
| `/billiard/booking/post`（扩展） | 面板详情增加回复、已接受球友、本人申请；发帖人另有申请列表 | 申请 id 和留言只给发帖人；本人只看到自己的申请 |
| `/billiard/booking/post/reply` | 回复 | 已登录、帖子开放、须知 |
| `/billiard/booking/post/apply` | 申请 | 帖子开放、有名额、不是发帖人、须知 |
| `/billiard/booking/post/withdraw` | 撤回本人的申请 | 本人、开始前 |
| `/billiard/booking/application/decide` | `accept` / `decline` / `remove` | **必须是该帖发帖人**、帖子开放、状态流转合法 |

状态流转：`pending → accepted / declined / withdrawn`；`accepted → withdrawn / removed`。其他一律拒绝。

新模型沿用 3.2 的权限：门户 / 公开用户无模型权限，只经路由；员工只读；管理员读写；不可删除；记录规则按 `website_id`。所有显示名经 `board_display_name()`。

## 五、关闭联动与通知

**关闭（BRD-015）**：在预约的 `write()` 里，状态变为已取消、已过期、未到场时，把帖子改为 `closed`。与预约变更同一事务，失败一起回滚。

**改期（BRD-017）**：预约的开始时间、时长或桌台变化时，帖子本身不存这些信息，显示自动更新，只需通知已接受的球友。

**邮件（BRD-018、019）**：

| 事件 | 收件人 |
|---|---|
| 新申请 | 发帖人 |
| 接受、拒绝、移除 | 申请人 |
| 帖子因预约变化关闭 | 已接受的球友 |
| 时段或桌台变更 | 已接受的球友 |

- 使用 2.2 的 Q Club 邮件版式、发件人和网站域名；发件人未设置时不发
- 内容：事件、时段、桌台、对方显示名、链接（`/billiard/booking?date=…&post=…`，打开对应帖子）
- 回复、撤回不发邮件；到开始时间自然关闭不发邮件
- 发送失败只记录日志，不影响操作本身，放进队列后由 Odoo 发送

## 六、测试

| 规格 | 测试 |
|---|---|
| BRD-010 | 长度边界；帖子关闭后被拒；未登录被拒 |
| BRD-011 | 发帖人不能申请；重复申请被数据库拒绝且返回友好提示；撤回后可重新申请；拒绝 / 移除后不可 |
| BRD-012 | 只有发帖人能决定；非法状态流转被拒；开始后不能撤回和移除 |
| BRD-013 | 两个独立事务并发接受最后一个名额，恰好一个成功；名额满后不能申请 |
| BRD-014 | 全流程后预约的时段、金额、状态不变，预约数量不变 |
| BRD-015 | 取消、过期、未到场时关闭；事务回滚时帖子不关闭 |
| BRD-017 | 改时段、时长、桌台后显示更新并通知已接受的球友，未接受的不通知 |
| BRD-018 / 019 | 每个事件的收件人和内容；内容无联系方式；发件人为空不发；发送失败不影响操作；AUSHARE、公司名不出现 |
| BRD-003 / 025 | 未登录响应不含姓名；回复和申请留言按纯文本显示（e2e 检查不执行）；申请留言不泄露给其他顾客 |
| BRD-026 / 027 | 门户用户直接 ORM / RPC 读写被拒；缺 CSRF 被拒；决定他人帖子的申请被拒；AUSHARE 404 |
| e2e | 顾客 B 申请、发帖人接受、标记变化；未登录点 Apply 登录后回到原帖；桌面与手机 |
