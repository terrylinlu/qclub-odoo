# 任务 5.1 设计：Table Board 实时看板与员工提醒（RT-001~007）

规格：`docs/spec/phase5.md`

## 一、整体方案

不新增持久化模型。看板是一个新的后台客户端动作（OWL 组件，走 `ir.actions.client`，和普通的 Odoo 列表/表单视图平级），打开时用 RPC 读一次 `qclub.table` + 当前正在进行的 `qclub.booking`（`state in ('arrived',) 或 (state in ('confirmed',) 且已过开始时间)` 之类的"此刻占用"判定，复用 `qclub_opening_hours.py` 里已有的时间工具），之后靠 Odoo 自带的 `bus.bus` 推送增量刷新，不整页轮询。

提醒（toast）走同一套 bus 机制，但不依赖看板页面是否打开——用一个 Systray 组件（挂在后台顶栏，所有后台页面都加载），全局监听该员工所属网站的频道，收到提醒就用 `notification` 服务弹 toast。

## 二、Bus 频道与消息

- 频道：`('qclub.staff', website_id)`，每个网站一个频道。
- 两类消息：
  - `qclub.board_update`：payload `{table_id, booking_id, state}`，看板组件收到后只重新拉该桌台的状态（不用整页刷新）。
  - `qclub.alert`：payload `{kind, booking_id, booking_name, table_name, start, end}`，`kind` 取值 `booking_submitted` / `deposit_confirmed` / `cancelled` / `player_joined`。Systray 收到后用 `notification` 服务弹 toast，文字按 `kind` 拼成英文句子（如 "New booking QB2026-00123 awaiting deposit"），不带金额和联系方式（RT-005）。
- 谁能订阅：员工/管理员登录后，前端读取其有权限访问的网站列表（复用现有 `allowed_company_ids` 的思路），对每个网站订阅 `qclub.staff` 频道；不是该网站员工的用户订阅不到，天然满足 RT-007 的网站隔离（而不是后端做权限过滤——bus 频道本身就是隔离边界，前端只会订阅它有权限看的网站）。

## 三、后端改动

新增 `addons/qclub_billiard/models/qclub_realtime.py`，一个 mixin 或者几个独立函数：

```python
def notify_board(env, booking):
    env['bus.bus']._sendone(('qclub.staff', booking.website_id.id), 'qclub.board_update',
                             {'table_id': booking.table_id.id, 'booking_id': booking.id, 'state': booking.state})

def notify_alert(env, booking, kind):
    env['bus.bus']._sendone(('qclub.staff', booking.website_id.id), 'qclub.alert',
                             {'kind': kind, 'booking_id': booking.id, 'booking_name': booking.name,
                              'table_name': booking.table_id.name,
                              'start': booking.start_datetime.isoformat(), 'end': booking.end_datetime.isoformat()})
```

在以下已有方法末尾各加一行调用（不改变它们原有的事务/返回值，纯粹追加副作用）：

| 事件（RT-004） | 挂在哪个已有方法 |
|---|---|
| 新预约提交（待付押金） | `qclub_booking.py` 的 `create()`（线上提交，不含员工后台手动创建——那条不算"顾客提交"事件） |
| 押金付款成功（确认） | `booking_deposit.py` 里把状态改成 confirmed 的那个写入点 |
| 取消 | `booking_deposit.py` 的 `_cancel_booking()` |
| 找球友有人被接受加入 | `qclub_board.py`（或等效文件）里接受申请的那个方法 |

`board_update` 消息额外挂在：到店（Arrived）、结算完成（Completed）、未到场没收（No-show）——这些改变"当前占用"状态但不在 RT-004 的四类提醒范围内，只刷看板不弹 toast。

## 四、前端改动

- `static/src/js/table_board.js`：OWL 组件，`ir.actions.client` tag `qclub_table_board`。用 `useBus` 订阅频道，收到 `qclub.board_update` 后用 RPC 增量拉该桌台最新状态更新 state；初次挂载时一次性 RPC 拉全部桌台当前状态。
- `static/src/js/table_board.xml`：模板，网格布局参考 `booking_grid.js` 对应的前端模板（顾客那边的网格），但这是独立的后台模板，不共用文件。
- `static/src/js/staff_alert_systray.js`：Systray 组件，`registry.category("systray")` 注册；useBus 订阅员工所有可见网站的 `qclub.alert`，收到后调用 `this.env.services.notification.add(...)`。
- 菜单：`views/qclub_menus.xml` 新增 "Table Board" 菜单项，action 类型 `ir.actions.client`，位置在 "Daily Reconciliation" 旁边，权限同 `group_billiard_staff`。

## 五、测试策略

- Python 层：`notify_board` / `notify_alert` 的调用点用 mock 断言被正确调用（参数里的 `kind`、`website_id`、不含敏感字段），不依赖真实 WebSocket。
- e2e（Playwright，`e2e/` 目录）：两个浏览器上下文，一个开 Table Board 页面（员工），一个走顾客预约流程（提交/付款/取消），断言员工页面在几秒内（不刷新）看到看板状态变化和 toast 文案，覆盖 RT-002、RT-004。
- 网站隔离：e2e 或 HTTP 测试验证 AUSHARE 员工订阅不到 Q Club 频道的消息（反之亦然）。

## 六、范围边界

不做：WebSocket 降级轮询、微信/Telegram webhook、提醒的"已读/认领"状态、历史提醒列表持久化（提醒就是一次性 toast，错过就错过，RT-006）。
