# 设计：任务 4.6 日对账报表（ST-003、ST-004、ST-008–012）

规格：`docs/spec/phase4.md` 第 E 节、第 G 节（场景数字）、`docs/spec/phase1-2.md` ST-003/ST-004。

## 1. 新增字段：`cancelled_at`

`addons/qclub_billiard/models/booking_deposit.py`：

- 新增 `cancelled_at = fields.Datetime(readonly=True, copy=False, index=True)`，加入 `DEPOSIT_FIELDS` 审计保护集合。
- `_cancel_booking()` 里，`super().write({'state': 'cancelled'})` 之后、分支判断之前，无条件 `self._write_deposit({'cancelled_at': fields.Datetime.now()})`（所有取消都记录，不止没收的）。

**为什么要加**：ST-009 要求"窗口内取消没收"按**取消发生的时间**归属营业日，但目前没有任何字段记录取消发生的时刻（`write_date` 会被后续任何写操作污染，不可靠）。没收没有专门时间戳，复用 `no_show_at`（已到场改为未到场时间戳，已存在）区分不开这两种没收渠道（都只是 `deposit_state='forfeited'`），所以要靠 `state`（`cancelled` vs `no_show`）区分渠道、靠各自专属的时间戳字段确定归属日。

## 2. 对账口径：7 + 1 个类目

ST-008 规定的 7 类资金事件 + 1 个你已批准新增的类目（结算差额留存，不属于 ST-008 原文但为了让自检②平衡）：

| 类目 | 金额计算 | 归属日字段 | 说明 |
|---|---|---|---|
| 押金收取 | `sum(paid_amount)` | `paid_at` | 在线预约付押金成功那一刻 |
| 押金退款 | `sum(refund_amount)` | `refund_at` | 取消退款、例外退款（RF-005）、多付退款都算 |
| 押金抵扣 | `sum(paid_amount)`，筛 `deposit_state='applied'` | `settle_at` | 结算时把押金抵进台费（含更正，更正不改 `settle_at`） |
| 窗口内取消没收 | `sum(paid_amount)`，筛 `state='cancelled' and deposit_state='forfeited'` | `cancelled_at`（新字段） | |
| 未到场没收 | `sum(paid_amount)`，筛 `state='no_show' and deposit_state='forfeited'` | `no_show_at` | 撤销未到场（Revert to Arrived）后 `deposit_state` 变回 `paid`，自然不再计入 |
| 现场 EFTPOS | `sum(balance_amount)`，筛 `balance_method='eftpos'` | `settle_at` | |
| 现场现金 | `sum(balance_amount)`，筛 `balance_method='cash'` | `settle_at` | |
| 结算差额留存（新增） | `sum(max(paid_amount - actual_table_fee, 0))`，筛 `state='done'` | `settle_at` | 实际台费低于已付押金时不退的差额（4.5 第 H.4 条）；不属于 ST-008 原文列出的类目，单独列一行，你已批准 |

所有类目都按 `website_id` 过滤（报表选的那个网站），金额都是**实时查询当前字段值**算出来的，不做快照/落库——同一天的报表，结算更正（Correct Settlement）之后再打开会自动反映最新结果，这是预期行为。

## 3. 两个自检等式

**自检①**（ST-010 第一条）：

```
押金收取 − 押金退款 − 押金抵扣 − 窗口内取消没收 − 未到场没收
    = 未了结押金当天净变化（独立算出）
```

"独立算出"不能只是把上面 5 个数字重新加减一遍（那样等式恒成立，测不出代码错误）。设计成两条完全不同的查询路径：

- 左边：上表 5 个类目各自的 SQL 聚合（已经按归属日过滤）。
- 右边：对每条"曾经付过押金"的预约（`paid_at` 有值），用当前 `deposit_state` 判断它的"退出时刻"：
  - `refunded` → 退出时刻 = `refund_at`
  - `applied` → 退出时刻 = `settle_at`
  - `forfeited` 且 `state='cancelled'` → 退出时刻 = `cancelled_at`
  - `forfeited` 且 `state='no_show'` → 退出时刻 = `no_show_at`
  - 其余（`paid`、`refund_failed` 等）→ 还没退出，退出时刻视为无穷大
  
  营业日开始时刻 `T0`、结束时刻 `T1`（6:00 AM 分界）下的"未了结押金"：
  ```
  outstanding(T) = sum(paid_amount)，筛 paid_at < T 且 (退出时刻为空 或 退出时刻 >= T)
  ```
  右边 = `outstanding(T1) - outstanding(T0)`。

两边都按 `compare_amounts` 四舍五入后比较，不等则标红。这是两条独立代码路径（一条是分类目 SQL 聚合，一条是按预约逐条判断状态），能测出"某类目漏统计了一条记录"这种真实 bug。

**自检②**（ST-010 第二条，含你已批准的新类目）：

```
当天结算的实际台费合计 + 结算差额留存 = 押金抵扣 + 现场EFTPOS + 现场现金
```

"当天结算的实际台费合计" = `sum(actual_table_fee)`，筛 `state='done' and settle_at 在当天`。

两个等式都在报表上显示为一行文字 + 绿色/红色标记（不等时标红），不等时旁边加一句小字提示"请人工核对"。

## 4. 模型与交互

新文件 `addons/qclub_billiard/models/reconciliation.py`，`TransientModel` `qclub.reconciliation`：

- 字段：`website_id`（Many2one 'website'，required）、`business_date`（Date，required，默认营业今天，用现成的 `business_today()`）、`company_id`（related `website_id.company_id`）、`currency_id`（related `company_id.currency_id`）。
- 8 个 Monetary 字段（上表类目）+ `settled_fee_total`（自检②左边的台费合计）+ 两个 Boolean（`check1_ok`、`check2_ok`）+ 两个 Monetary 存差值用于页面显示（`check1_left`/`check1_right`、`check2_left`/`check2_right`）。
- 这些都是 `compute`（非 store），`@api.depends('website_id', 'business_date')`，整段逻辑在一个私有方法里一次算完所有类目（避免 8 次独立查询各自重复算营业日时间范围）。
- 营业日时间范围：复用 `qclub_opening_hours.py` 的 `BUSINESS_TZ`/`BUSINESS_DAY_CUTOFF` 常量，新写一个小helper（同文件或 `reconciliation.py` 里新增）把 `business_date` 转成 `[T0, T1)` 的 UTC `naive` datetime 二元组，给 ORM domain 用。

**点开数字**：每个类目字段旁边放一个按钮（stat button 或普通 `<button>`），对应 `action_view_<category>()` 方法，`ensure_one()`，构造好 domain（类目定义表里那一列）返回：
```python
{'type': 'ir.actions.act_window', 'res_model': 'qclub.booking', 'view_mode': 'list,form',
 'domain': domain, 'name': _('<类目中文/英文名>')}
```
点开后是标准 Odoo 列表视图，可以再点进每条预约看详情（你已选的方案：跳转列表视图）。

**视图**：一个 form 视图，上方 `website_id`/`business_date` 选择器，下面 8 行"类目名 + 金额 + 查看按钮"，再下面两行自检结果（文字 + 颜色，用 `decoration` 或简单的 `t-attf-class`）。挂到现有的 Billiard 根菜单下，新增菜单项 "Daily Reconciliation"（`menu_billiard_reconciliation`，`parent="menu_billiard_root"`）。

## 6. Excel 导出（ST-011，你已选"摘要+明细两个 sheet"）

新增一个 controller 路由（如 `/billiard/reconciliation/export/xlsx`，或者直接在 wizard 上放一个 `type="object"` 按钮调用返回 `ir_actions_act_url` 式下载，参照 Odoo 常见"下载 xlsx"模式）：

- 用 Odoo 自带的 `xlsxwriter`（已经是 Odoo 核心依赖，不算新增外部依赖）直接写 `BytesIO`，通过 `request.make_response` 返回 `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`。
- 鉴权：路由必须校验当前用户在 `group_billiard_staff`/`group_billiard_manager` 且 `website_id` 属于其可访问公司，否则 403（不能单靠 wizard 按钮本身的 ACL，因为是一个独立 HTTP 路由）。
- **Sheet 1 "Summary"**：8 个类目名+金额、两个自检等式的左右值和是否平衡。
- **Sheet 2 "Detail"**：当天所有相关预约的明细行——预约编号、球桌、顾客、所属类目（可能一条预约同时出现在多个类目里，比如场景1同时是"押金抵扣"和"EFTPOS"，各占一行）、金额、事件时间。按类目分组或者加一列"类目"方便筛选。
