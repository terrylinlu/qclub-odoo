## 二、命令

| 命令 | 行为 |
|---|---|
| `make demo` | 确保 db 运行 → 若 `qclub_demo` 不存在则构建（见第三节）→ 升级本模块（`-u qclub_billiard`，让最新代码生效）→ 后台启动演示服务 → 等待 `/web/health` 返回 200 → 打印访问地址和演示账号 |
| `make demo-reset` | 停止演示服务 → `DROP DATABASE qclub_demo` 并清理其文件存储 → 执行 `make demo` |
| `make demo-stop` | 只停止演示服务，保留演示库（新增，规格未列，方便日常使用） |
| `make demo-logs` | 跟踪演示服务日志（新增，同上） |

护栏：演示库名固定为 `qclub_demo`，写死在 Makefile 中且同样经过 `guard` 检查（必须以 `qclub_` 开头）。`demo-reset` 只删除这一个库。

## 三、演示库构建流程

1. `CREATE DATABASE qclub_demo TEMPLATE qclub_base`：复用已有基础模板库（已含依赖模块、`btree_gist`、两个网站、AUD、Adelaide 时区），几秒完成
2. 安装本模块：`odoo -d qclub_demo -i qclub_billiard --without-demo=True --stop-after-init`
3. 写入演示数据：`odoo shell -d qclub_demo --no-http < docker/demo_data.py`

演示数据脚本 `docker/demo_data.py` 的原则：
- **幂等**：按登录名、网站名查找后再创建或更新，重复执行不报错、不产生重复记录
- **标注为演示**：所有演示记录的名称带"【演示】"前缀；账号登录名以 `demo-` 开头
- **分段守卫**：桌台、营业时间等模型要到任务 1.1、1.2 才存在，脚本用 `if "模型名" in env` 跳过尚不存在的部分；后续任务只需往对应分段里填数据

本任务（1.0）的骨架只写入：

| 数据 | 内容 |
|---|---|
| 网站域名（DEMO-003） | Q Club → `http://qclub.localhost:8069`；AUSHARE → `http://aushare.localhost:8069` |
| 后台地址 | `web.base.url` = `http://localhost:8069` |
| 管理员 | 沿用 `admin` 账号，密码设为占位值 `admin`（仅本机演示库） |
| 演示员工 | `demo-staff`，内部用户；"球厅员工"组在任务 1.1 建立后由脚本补加 |
| 演示顾客 | `demo-customer-a`、`demo-customer-b`，门户用户（阶段 2 下单、阶段 3 约球用） |
| 占位桌台、营业时间 | 仅留空分段，任务 1.1、1.2 填入（中式八球、斯诺克、九球各 1 张，营业时间按规格第 G 节） |

演示账号密码统一为占位值 `demo`，符合 AGENTS.md 规则 2 的例外（仅绑定 127.0.0.1 的演示库占位账号），不与任何真实环境相同。

## 四、Docker 配置

在 `docker/docker-compose.test.yml` 中新增服务 `demo`，与测试共用同一个 PostgreSQL 容器（库名隔离：`qclub_test` 与 `qclub_demo`）：

```yaml
  demo:
    image: <与 odoo 服务相同的固定摘要>
    depends_on: { db: { condition: service_healthy } }
    environment: <同 odoo 服务>
    volumes:
      - ../addons:/mnt/extra-addons:ro
      - odoo-demo-data:/var/lib/odoo        # 文件存储与测试分开
    ports:
      - "127.0.0.1:8069:8069"               # 仅本机
    command: ["odoo", "-d", "qclub_demo", "--db-filter=^qclub_demo$", "--no-database-list",
              "--without-demo=True", "--proxy-mode"]
```

- `--db-filter` 与 `--no-database-list`：演示服务只能看到 `qclub_demo`，不会误连其他库
- 端口冲突：现有 `odoo` 服务（预留给阶段 2 的 e2e）也映射了 `127.0.0.1:8069`。**建议**本任务把它改为 `127.0.0.1:8070`，演示固定用 8069（与规格中的地址一致）。`make test` 用 `run` 启动，不映射端口，不受影响
- 影响：`make reset`（`down -v`）会连同演示库一起删除，在 `make help` 中注明

## 八、实现时与本设计的差异

1. **文件存储**：原计划演示服务单独用一个数据卷。实测基础模板库 `qclub_base` 有约 3.6 MB 文件存储（网站图片等），以它为模板建库时必须一起复制，否则网站缺图。因此演示服务与 `odoo` 服务共用 `odoo-data` 卷（文件存储本来就按库名分目录），建库时把 `filestore/qclub_base` 复制为 `filestore/qclub_demo`；`demo-reset` 只删除 `filestore/qclub_demo` 和会话目录
2. **去掉 `--proxy-mode`**：演示环境前面没有反向代理，不需要
3. **compose 写法**：`demo` 服务用 YAML 锚点继承 `odoo` 服务的镜像和配置，镜像摘要只写一处，升级时不会漏改
