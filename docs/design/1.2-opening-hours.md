## 一、规格要点

- TBL-004：营业时间按星期配置，可设休息日；起止必须为整点；结束时间可晚于 24:00（跨午夜），跨午夜的时段归属开始那一天
- TBL-007：提供初始营业时间（第 G 节：周一至周四 14:00–24:00，周五 14:00–次日 02:00，周六 13:00–次日 02:00，周日 13:00–24:00），用于测试环境和首次配置参考；后台可修改
- AGENTS.md：时间以 UTC 存库，按 `Australia/Adelaide` 计算；所有时段判断须在该时区下测试，并覆盖夏令时切换日

## 二、数据模型 `qclub.opening.hours`

每条记录是某个网站在某个星期几的**一段**营业时间。

| 字段 | 类型 | 说明 |
|---|---|---|
| `website_id` | Many2one website，必填 | 与桌台、配置一致按网站隔离 |
| `weekday` | Selection 0–6（Monday … Sunday），必填 | 该时段**开始**的那一天，即归属日 |
| `open_hour` | Integer，必填 | 开始小时，0–23 |
| `close_hour` | Integer，必填 | 结束小时，可大于 24 表示次日；如 26 = 次日 02:00 |
| `display_name` | 计算 | 如 "Friday 14:00 – Saturday 02:00" |

**为什么用整数小时而不是时间字段**：规格要求起止必须是整点，整数从根本上排除了 14:30 这类值；`close_hour > 24` 直接表达"跨午夜、归属开始日"，不需要额外的"次日"标志。

**校验（TBL-004）**：
- `0 ≤ open_hour ≤ 23`
- `open_hour < close_hour ≤ open_hour + 24`（一段最长 24 小时）
- 同一网站同一星期内多段不能重叠；**跨午夜的时段与次日的时段也不能重叠**（如周五 14–30 与周六 05–… 冲突）。周日跨午夜的时段与周一比较
- 同时有 Python 约束（英文提示）和数据库 CHECK 约束兜底（前两条；重叠检查只能在 Python 里做）

**休息日**：某个星期几没有任何时段即为休息日，不需要单独的开关。

## 三、时段计算（供任务 1.3、2.1 使用）

提供一个服务端方法，后续的预约校验（BK-002）和占用网格（2.1）都只用它，不各自重算：

`qclub.opening.hours._get_business_intervals(website, business_date)`
→ 返回该营业日（按归属日）所有营业时段的 `[(start_utc, end_utc), ...]`，UTC naive datetime（与 Odoo 存库一致）。

计算方法：在 `Australia/Adelaide` 下把 `business_date + open_hour` 与 `business_date + close_hour`（可跨到次日）转成本地时间，再换算 UTC。

**夏令时规则**（阿德莱德，已用时区库核实）：
- 2026-04-05（周日）03:00 ACDT 回拨到 02:00 ACST：本地 02:00–03:00 出现两次
- 2026-10-04（周日）02:00 ACST 跳到 03:00 ACDT：本地 02:00–03:00 不存在

约定：
- 本地时间出现两次时，取**第一次**（即仍在夏令时内的那个）
- 本地时间不存在时，顺延到切换后的同一时刻（即 03:00）
- 按规格 G 节的营业时间，周六营业到次日 02:00，**正好在切换点之前结束，营业时长不受影响**（实测：两个切换周末的周六都是 13 个实际小时）；但这两个周末前后的 UTC 换算偏移不同（+9:30 与 +10:30），必须有测试覆盖
- 阿德莱德是半小时时区：本地整点对应 UTC 的 :30，测试要检查这一点

## 四、初始营业时间（TBL-007）

**不在模块安装时自动写入**。原因：生产库里 Q Club 和 AUSHARE 共用一个库，安装时自动给网站加营业时间可能误加到 AUSHARE，也可能覆盖已有配置。

改为：
- 提供 `qclub.opening.hours._load_default_hours(website)`：仅当该网站还没有任何营业时间时，按第 G 节写入 7 段；已有时不做任何改动
- 在 Billiard Settings 表单上加一个按钮 **Load Default Opening Hours**（仅管理员可见，该网站已有营业时间时隐藏）
- 演示数据（`docker/demo_data.py`）对 Q Club 调用它

## 八、需要你确认的问题

1. **营业时间按网站统一，而不是按桌台分别设置**：所有桌台共用 Q Club 的营业时间。规格 BK-002 写的是"该桌某一个营业时段"，按网站统一时每张桌的营业时段就是网站的营业时段。如果将来有个别桌台时间不同（比如某张桌晚开），再加按桌覆盖。同意吗？
2. **一天允许多段**（如 10:00–14:00、17:00–24:00 中间休息）：规格没禁止，模型天然支持，同意吗？
3. **初始营业时间不自动写入**，而是通过按钮 / 演示脚本写入（理由见第四节），同意吗？
4. **夏令时约定**：本地时间出现两次取第一次、不存在则顺延（第三节）。目前的营业时间不会碰到这种情况，这只是为将来改营业时间预留的规则，同意吗？
5. **公共假日**：按规格第 I 节，一期不做，需要时手动改当天营业时间或停用桌台。确认维持吗？
