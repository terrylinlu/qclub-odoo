## 一、为什么需要数据库约束

任务 1.3 的冲突检查在 Python 里做：先查有没有重叠的有效预约，没有再插入。两个人**同时**下单时，两个事务都看不到对方尚未提交的预约，都会通过检查，结果同一时段被约两次。只有数据库层的约束能在并发时保证"恰好一个成功"。

## 二、排他约束（BK-004）

按 AGENTS.md 第 7 节，在 `qclub.booking` 的 `init()` 中创建（已有则跳过）：

```sql
ALTER TABLE qclub_booking ADD CONSTRAINT qclub_booking_no_overlap
  EXCLUDE USING gist (
    table_id WITH =,
    tsrange(start, "end", '[)') WITH &&
  ) WHERE (state IN ('pending', 'confirmed', 'arrived'));
```

- `btree_gist` 已在基础库启用（冒烟测试 `test_002` 保证）
- `[)` 半开区间：15:00–17:00 与 17:00–19:00 相邻不算重叠，与 1.3 的 Python 检查一致
- `WHERE` 只约束三种有效占用状态，与 1.3 的 `ACTIVE_STATES` 一致；取消、过期、未到场、完成的预约不占用（BK-006 在数据库层同样成立）
- 生产库安装前提：PostgreSQL 管理员能执行 `CREATE EXTENSION btree_gist`（`progress.md` 第六节的待办，上线前必须确认）

1.3 的 Python 检查保留：它在单人操作时给出即时、清楚的提示；数据库约束是并发时的最后一道防线。

## 三、冲突提示（ADM-003）

数据库约束触发时，PostgreSQL 抛出 `ExclusionViolation`。在 `create()` 和 `write()` 中捕获它（`write()` 需先 `flush` 才能在方法内触发），转换为英文 `ValidationError`：

> This table is already booked for the selected time. Please choose another time or table.

用户不会看到 SQL 报错或约束名。

## 四、并发测试（BK-005）

规格要求"在真实 PostgreSQL 上测试，不 mock"。Odoo 的普通测试在一个事务里运行、最后回滚，无法模拟两个独立事务。做法：

1. 测试开始时，用**独立的数据库连接**创建并**提交**测试所需的桌台、营业时间等数据
2. 两个线程各开一个独立连接，同时为同一桌台创建重叠预约（用屏障同步，让两边几乎同时插入）
3. 断言：恰好一个提交成功；另一个得到第三节的 `ValidationError`（底层是 `ExclusionViolation`），而不是超时或其他错误
4. 测试结束时（无论成败）用独立连接删除第 1、2 步提交的全部数据

测试库每次 `make test` 都从模板重建，即使清理失败也不会影响下一次运行；但同一次运行里的其他测试必须不受影响，所以清理放在 `finally` / `addCleanup` 中。

## 五、过期释放（BK-008）

- **定时任务**：`ir.cron` "Billiards: expire unpaid bookings"，**每 1 分钟**运行一次，调用 `qclub.booking._cron_expire_pending()`：把 `state = pending` 且 `lock_expire <= 现在` 的预约置为 `expired`（复用 1.3 的 `_action_expire`，遵守状态白名单）
- **按需过期**：新建预约或改时间时，先把**同一桌台**上已超过锁定时间的待付押金预约置为过期，再做冲突检查。这样即使定时任务还没轮到，过期的锁也不会挡住新预约（否则最多会多占 1 分钟）
- 只有系统能过期预约，界面上没有"过期"按钮（与 1.3 一致）
- 定时任务以超级用户运行；批量处理时一条失败不影响其他（逐条处理并记录日志）
