# 任务 5.2 设计：看板加当天剩余安排 + 提醒进收件箱（RT-001/003/006/008/009 修订）

规格：`docs/spec/phase5.md`（2026-11-19 修订）。承接 task-5.1-v1 已合并的实现，不推翻原有 bus 频道/组件结构，只做增量修改。

## 一、起因

task-5.1-v1 上线后员工实测反馈：
1. 看板只显示"此刻占用"，员工现场肉眼就能看出来，价值有限。
2. 未来预约员工在顾客预约页面已经能看到，看板不需要重复做成多日视图。
3. toast 错过了就彻底没了，员工不可能一直盯着电脑，需要一个能回看的地方。

归纳后的真实需求：看板要变成"员工管理当天现场桌台的工作主页面"——每张桌子不只看此刻状态，还要看当天剩下的安排；提醒除了弹窗，还要留痕可查。

## 二、看板：当天剩余安排

`qclub_realtime.py` 的 `get_table_board` 在现有"此刻占用"查询之外，对每张桌子额外查询：

```python
upcoming = self.env['qclub.booking'].search([
    ('table_id', '=', table.id), ('state', '=', 'confirmed'),
    ('business_date', '=', day), ('start', '>', now),
], order='start')
```

返回结构在现有 `booking` 字段旁加一个 `upcoming` 列表字段，每项只含 `{'start': ..., 'end': ...}`（不含 `id`/`name`/顾客姓名——当天安排列表不需要员工在客人到店前识别身份，维持 RT-005/RT-009 一致的最小信息暴露原则）。

前端 `table_board.xml`/`table_board.js`：空闲卡片下方加一个小列表渲染 `upcoming`（时间用现有的 `Intl.DateTimeFormat` Adelaide 本地化格式，跟占用卡的结束时间同一套格式化函数）；占用卡维持原样，不额外显示 upcoming（当前这条占用结束后下一条才算 upcoming，若需要可以在结束时间旁顺带展示，具体由实现判断最简洁的展示方式，不强制）。

`qclub.board_update` 消息本身不需要改 payload（仍是 `{table_id, booking_id, state}`，前端收到后照旧对该桌子重新发一次 `get_table_board` 式的单桌刷新 RPC，取最新的"此刻 + 当天剩余"数据——这是现有增量刷新机制，只是刷新后拿到的数据多了 upcoming 字段）。

## 三、补齐 board_update 推送缺口

现状：`booking_deposit.py` 的押金确认写入点（`_receive_deposit` → `_write_deposit`，[booking_deposit.py:163](../../addons/qclub_billiard/models/booking_deposit.py)）和取消（`_cancel_booking`，[booking_deposit.py:276](../../addons/qclub_billiard/models/booking_deposit.py)）只调用了 `notify_alert`，没有调用 `notify_board`。

这在 5.1 里不算问题（看板只看此刻，一个刚确认的未来预约本来就不影响此刻占用的显示）；但现在看板要显示"当天剩余安排"，这两个事件必须同时推 `notify_board`，否则客人刚付完押金，这条预约不会马上出现在看板的"当天剩余"列表里，取消了也不会马上从列表消失，要等别的事件（到店/结算）顺带刷新才会更新。

改动：两处各补一行 `notify_board(self.env, self)`，紧跟在已有的 `notify_alert(...)` 调用旁边，纯追加，不改变原有事务/返回值。

## 四、提醒进收件箱

`qclub.booking` 已经 `_inherit = ['qclub.booking', 'mail.thread']`（[booking_deposit.py:26](../../addons/qclub_billiard/models/booking_deposit.py)），现有代码已经在用 `message_post` 记日志（押金确认、取消等），只是没人被通知。

在 `qclub_realtime.py` 新增一个小函数，按网站找出该网站当前能访问的员工/管理员（跟 `staff_websites` 的权限判断对称，反过来从网站找用户）：

```python
def staff_users(env, website):
    return env['res.users'].sudo().search([
        ('groups_id', 'in', [
            env.ref('qclub_billiard.group_billiard_staff').id,
            env.ref('qclub_billiard.group_billiard_manager').id,
        ]),
        ('company_ids', 'in', website.company_id.ids) if website.company_id else (1, '=', 1),
    ])
```

（具体查询条件按现有公司权限模型写法对齐 `staff_websites`，不是最终代码，实现时核对一致。）

`notify_alert(env, booking, kind)` 在原有 `_sendone` 之后，追加：

```python
staff = staff_users(env, booking.website_id)
if staff:
    booking.message_notify(
        partner_ids=staff.mapped('partner_id').ids,
        subject=booking.name,
        body=<与 toast 相同的文案>,
    )
```

文案复用前端 `staff_alert_systray.js` 里按 `kind` 拼句子的同一套措辞（后端这边用 Python 侧的等价文案，两边保持一致，不必共用同一份代码，但措辞对齐）。

`message_notify` 不依赖是否在线，收件人标记已读前一直留在 Discuss 收件箱/顶部消息按钮里，天然满足"错过 toast 也能找回来"的要求，不需要新建模型或历史列表页面。

## 五、测试策略

- `test_rt_003_...`：看板返回的 `upcoming` 列表只含已确认、当天、未来开始的预约，按时间排序，不含 pending；不含顾客姓名/预约编号字段。
- `test_rt_002_...`（或新增一个）：押金确认和取消都会触发 `notify_board`（mock 断言），不止 `notify_alert`。
- `test_rt_008_...`：`notify_alert` 会调用 `message_notify`，收件人是该网站的员工/管理员（按公司权限过滤，AUSHARE 员工收不到 Q Club 的），文案不含金额/联系方式；非 staff 用户不在收件人列表里。
- 现有 314 个测试需保持全绿，`make lint test iso-check` 不变。

## 六、范围边界（不变）

不新增持久化历史列表页面（收件箱本身就是历史记录，不用再造一个）；不支持看板上直接操作（到店/结算仍走原入口）；不做多日/日期切换视图；不做已读/认领状态同步到 toast。
