这是任务 4.4 验收过程中追加的两个新需求的实现任务。设计已经批准，分别写在：

- `docs/spec/phase4.md` 第 C 节 `NS-006`、第 H 节第 12 条
- `docs/spec/phase1-2.md` 第 A 节 `CFG-007`、`docs/spec/phase4.md` 第 H 节第 13 条
- `docs/design/4.4-no-show.md` 文件末尾两段追加内容（"追加：NS-006 到店确认邮件" 和 "追加：CFG-007 通知邮件可配置开关"）——**请先完整读这两段，里面有具体的方法名、字段名、调用点和表格**

## 范围限制

只能改：`addons/qclub_billiard/`、`e2e/`、`docs/`、`tools/`。不要改 `Makefile`、`docker/`、`.github/`。

## 任务 1：NS-006 到店确认邮件

1. `addons/qclub_billiard/models/booking_no_show.py` 新增 `_queue_arrival_email()`，写法完全模仿同文件里已有的 `_queue_no_show_email()`（同样的 try/savepoint/sudo/send_after_commit/异常吞掉记日志的模式），但：
   - 邮件模板用新的 `qclub_billiard.arrival_email`
   - 不传 `amount`，正文不显示任何金额
   - 和 `_queue_no_show_email` 一样，不按 `booking_channel` 限制，只要 `partner_id.email` 和 `config.booking_email_from` 都有值就发（这点和 `_queue_cancellation_email`/`_queue_booking_email` 的 `online`-only 限制不同，不要照抄那两个）
2. 两个调用点：
   - `action_arrive()`：在 `super().action_arrive()` 成功返回后调用
   - `_revert_no_show()`：在写完 `state: 'arrived'` 那次 `_write_deposit(values)` 之后调用
3. `addons/qclub_billiard/views/deposit_payment.xml` 新增 `arrival_email` 的 `ir.ui.view` 记录，`model="qclub.booking"`，样式照抄 `no_show_email` 那条记录，正文用类似："Your booking is confirmed as arrived. See you at the table!"，带预约编号、台桌、时段（时段参考其他邮件模板怎么取 `booking.start`/`booking.end`/台桌名称的写法），不显示金额。

## 任务 2：CFG-007 通知邮件开关

1. `addons/qclub_billiard/models/qclub_config.py` 新增 5 个 `Boolean` 字段，`default=True`，参考设计文档里给的字段名和 `help` 文案：
   `notify_booking_received`、`notify_deposit_confirmed`、`notify_cancellation`、`notify_no_show`、`notify_arrival`
2. 后台配置表单（找 `qclub_config` 对应的 view 文件，可能叫 `qclub_config_views.xml` 之类）加一个 "Notifications" 分组放这 5 个字段。权限不用额外处理，`qclub.config` 整个模型已经是管理员可写、员工只读。
3. 在下面 5 个方法里各加一行开关判断（放进已有的"有收件人才发"判断里，不要单独拆一个 if）：

   | 方法 | 文件 | 开关字段 |
   |---|---|---|
   | `_queue_booking_email` | `qclub_booking.py` | `notify_booking_received` |
   | `_queue_deposit_email` | `booking_deposit.py` | `notify_deposit_confirmed` |
   | `_queue_cancellation_email` | `booking_deposit.py` | `notify_cancellation` |
   | `_queue_no_show_email` | `booking_no_show.py` | `notify_no_show` |
   | `_queue_arrival_email`（任务 1 新增的） | `booking_no_show.py` | `notify_arrival` |

   例如 `_queue_booking_email` 原来是：
   ```python
   if self.booking_channel != "online" or not config.booking_email_from or not self.partner_id.email:
       return
   ```
   改成：
   ```python
   if not config.notify_booking_received or self.booking_channel != "online" or not config.booking_email_from or not self.partner_id.email:
       return
   ```
   其余 4 个方法同样的改法，各自加对应的开关字段。

   关掉开关只影响发不发邮件，不能影响状态流转、押金没收/退款、审计字段这些业务逻辑——这些逻辑都在调用 `_queue_*_email`之前已经执行完了，正常不会受影响，但写测试时要专门断言这一点。

## 测试

新增/扩充测试，覆盖设计文档里列的边界/反向点，每条编号测试要能对应到 NS-006 或 CFG-007：

- `test_no_show.py`：`action_arrive()` 和 `_revert_no_show()` 成功后各发一封到店邮件，正文不含金额；没有 `partner_id.email` 时静默跳过不报错；两条路径各自只发一封不重复（可以用 `mail.mail` search_count 断言）
- 新建 `test_cfg_notify_toggle.py`（或并入看起来最相关的现有测试文件也可以，你判断）：
  - 5 个开关默认值都是 `True`
  - 每个开关关掉后，对应事件不再产生新的 `mail.mail` 记录，但状态流转/押金处理/撤销照常完成（断言业务逻辑不受影响）
  - 非管理员（员工）写这些字段被拒绝（复用现有 CFG-004 相关测试的写法）
  - 多网站隔离：网站 A 关掉不影响网站 B 的发信

不要动已有测试的断言强度；如果某个已有测试因为新增的开关默认值（`True`）而需要调整 setUp 顺序或 mock，先确认默认值是 `True`（即默认行为和改之前完全一样，正常不该需要改已有测试）。
